The 30-second frame

What is mailflow?

A library other programs plug into. On every new email it fetches → cleans → emits a tidy structured record — handling auth, throttling, duplicates and broken mail for you.

Mental model — an automated mailroom. A letter arrives → the clerk is pinged → the clerk fetches the letter using a bookmark (never the ping) → opens it, pulls out the useful parts, discards junk → hands a summary card to the department that asked. Everything that follows is how that mailroom is built.
  • Watches a live inbox (Gmail in V1) for new mail
  • Produces a clean EmailEvent — sender, subject, plain-text body, thread key, fingerprint
  • Promises stable contracts so consumers build against it without fear of breakage

Pipeline · stage 1

Wake signal & webhook verification

A5reduced → Gmail OIDC-JWT

"A new-mail ping arrived — but is it really from Google, and is it safe to act on?"

Contract
WebhookVerifier port returns identity only (verified subscription / mailbox) — never payload trust.
V1 impl
Gmail Pub/Sub OIDC-JWT — signature via JWKS, audience, issuer. (Outlook validationToken handshake deferred.)
Why it matters
Push is internet-facing — anyone could forge a ping. A verified ping still only earns a wake, never "fetch this exact ID."

Pipeline · stage 2 · the golden rule

Fetch & cursor

A1A3B6Gmail compliant

"On wake, re-derive what changed from a durable bookmark — never trust the ID inside a ping."

Contract
Cursor is durable, strictly monotonic (commit_if_ahead), and advances on every terminal disposition. Gmail = historyId; Outlook = deltaLink.
Why it matters
Pings can be forged, duplicated, or reordered. The bookmark is the only trustworthy "where I stopped" — a crash resumes exactly there, no gaps, no re-scans.
V1 status
Gmail re-derives from historyId and commits one cursor per page (B6 ✓). Outlook wake-rewire is deferred.

Pipeline · stage 3

Size guard — fail closed

B1to fix

"If we can't tell how big an email is, assume it's too big and set it aside — before downloading."

Behavior
Unknown / omitted size ⇒ treat as over-limit ⇒ DLQ before fetch. (Today an unknown size becomes 0 and sneaks under the ceiling — the bug.)
Why it matters
"Fail open" on size lets an unbounded payload load into memory and crash the run. The safe default is to reject, not guess.

Pipeline · stage 4

Extract fields & thread key

A7to build

"Open the envelope, pull out sender / subject / body / attachments — and the ID that groups a conversation."

Contract
New thread_key on CleanEmail; maps Gmail threadId / Outlook conversationId, with a subject-normalized fallback.
Seam
MimeExtractor.extract_bytes(...) for raw RFC822 (Gmail); other providers implement extract(msg, env) directly (Outlook/Graph).
Why it matters
Without a provider-native thread key, consumers can't tie a reply back to its original — conversation grouping breaks.

Pipeline · stage 5

Clean — HTML → text

A6B5to build

"Turn an email's HTML into readable plain text — gently by default, aggressively only if asked."

Contract
ContentCleaner port (clean(CleanEmail) -> CleanEmail), wired as a real pipeline stage — not a post-emit afterthought.
Parity (B5)
A shared HTML→text converter runs in both extractors, so an HTML-only email yields non-empty body_text identically across providers.
Why it matters
V1 is plain-text-only (no HTML renderer). If HTML-only mail produced blank text, the product would look empty. This stage is what makes the output usable.

Pipeline · stage 6

Emit event & idempotency

A4key not yet on wire

"Hand the consumer a clean event stamped with a fingerprint so they can spot duplicates."

Contract
idempotency_key on EmailEvent = (tenant, mailbox, provider_message_id). Wire schema bumps 1.0 → 1.1 (additive).
Delivery
At-least-once, documented honestly. Exactly-once is not promised; duplicates are expected and handled by the key.
Why it matters
The emitted event is the public contract. The fingerprint is already computed internally — V1 simply exposes it so consumers needn't rebuild it.

Cross-cutting

Reliability — isolation, backoff, storm containment

B2B4partial

"The difference between 'one bad email' and 'the whole run dies.'"

DLQ isolation (B2)
One broken/oversized message is set aside alone — never crashes the batch. Counted exactly once (add_dead_letter() + paired trace). Gap: the fetch stage still lacks per-record isolation.
Backoff + storm (B4)
Retry 5xx; exponential backoff + jitter honoring Retry-After; bounded concurrency cap; and crucially contain an exhausted-retry storm so it can't abort the run.
Today's bug
A 429 storm propagates uncaught and takes everything down — exactly what B4 fixes.

Direction

Scope & roadmap

V1 in one line: a Gmail-only, single-tenant, poll-authoritative library (Gmail push only wakes the poller), cleaning each email to plain text and emitting a clean, de-duplicatable event.
P0 · V1

Frozen contracts + correctness defects: A2 taxonomy, A4 idempotency_key, A5 Gmail verify, A6 cleaner, A7 thread key, A10 overrides, A11 sync/version; B1–B5.

P1 · should-have

Subscription-renewal driver, missed-email backfill, attachment streaming + dedup, replayable DLQ, reference blob store, fuller observability.

P2 · post-V1 seams

Rich cleaning heuristics, HTML sanitizer, malware scanner, KMS encryption, S3 stores, async inbound buffer, persistent dedupe, GDPR DSAR, bounce engine.

P3 · future

Plugin kind registry, iCalendar parsing, TNEF decode, encrypted Graph resource-data, more providers (IMAP, SES).

Deferred out of V1: Outlook live (A1/C1/C2), GDPR erase + encryption (A9), PII redaction, multi-tenant, multi-worker, strict ordering, HTML sanitizer.
