01 · Executive summary

What we are shipping, and the one decision behind it

mailflow lets any app subscribe to "clean email events" instead of wrestling with Gmail APIs, authentication, throttling, duplicates, and broken messages. We build that capability once, as a shared library, and every downstream product reuses it.

GmailThe live provider in V1. The design is provider-agnostic; Outlook is a fast-follow.

The headline decision

Deliberately narrow the first release — Gmail-only, single-tenant, poll-driven — and spend the budget on getting the public contracts right. Those contracts are promises other teams build against; once published they cannot change without breaking everyone. Everything else is sequenced behind V1 with the seams already designed in.

What the business gets

  • Reuse, not rebuild: one hardened email connector that every product shares.
  • Clean inputs: sender, subject, readable body and attachments — no raw-email parsing downstream.
  • Safe by default: broken, oversized or poisonous messages are set aside, not allowed to jam the line.
  • Honest delivery: a duplicate fingerprint on every event so consumers can de-duplicate cheaply.

What V1 unlocks next

  • A proven, provider-agnostic foundation — adding Outlook later is adapter work, not a redesign.
  • A stable public contract teams can start building products against now.
  • A clear, low-risk path to richer features (attachments, filtering, recovery) as fast-follows.

03 · The scope decisions & why

Eleven deliberate trade-offs that made V1 shippable

On 2026-06-29 we closed every open scope question. Each choice trades breadth for a release we can ship with confidence — and each leaves the door open for what was deferred.

DecisionChoiceWhy it makes sense — and the consequence
Which email providerGmail, end-to-endGmail is already built and tested. One working provider proves the design is provider-agnostic — a claim, otherwise. Outlook stays in the codebase as a fast-follow.
Push vs. pollPoll is authoritativePings can be forged, dropped or reordered, so we never trust them to deliver mail. Push only wakes the poller sooner. The reliable engine is polling from a durable bookmark.
How many customersSingle-tenantA POC doesn't need multi-customer isolation yet. Dropping it shrinks the credential work substantially and removes a large chunk of effort.
ConcurrencySingle worker, synchronousOne-thing-at-a-time is simpler and correct. Multi-worker machinery is designed-for but deferred — and declared so, so adding it later isn't a breaking change.
Delivery guaranteeAt-least-onceExactly-once across networks is impractical. We promise at-least-once honestly and make duplicates cheap to detect with a fingerprint — a real promise beats a false one.
Login modelDelegated OAuth tokenOne OAuth token per mailbox keeps the credential handler simple — the only must-have is saving rotated tokens so the next run doesn't break.
HTML email handlingPlain text onlyNo HTML rendered to a UI in V1, so no sanitizer is needed. But the HTML→text converter becomes important — without it, HTML-only mail would arrive blank.
WebhooksGmail push as a wake-triggerKeeps a reduced verification scope: prove the Gmail ping is genuine (signed token) and nothing more. The Outlook handshake is deferred.
GDPR erase / encryptionOut of V1We own all the storage, so data-erasure and at-rest encryption can be added later without breaking anyone. Real GDPR tooling is a later milestone.
PII redaction in logsDeferred post-V1Full email bodies simply aren't logged by default in V1, so the risk is contained while the scrubbing feature waits.
Outlook live supportDeferred (fast-follow)Outlook's live-API quirks (subscription limits, size probe) are isolated work, not architecture. Deferring them removes about a third of the remaining effort.
The pattern: every cut is either already designed-for (so it slots in later cleanly) or safe to add without breaking consumers. None of them paints us into a corner.

04 · The risk that matters

Why the contracts are the thing to get right

The risk in a shared library is not the code that works today — it is the promises. A contract is a method shape, a data field, an error type, or a delivery guarantee that, once V1 ships, every consumer builds against. Change one later and you force a rewrite on everyone who trusted it.

This is why we freeze the public contracts before any parallel build begins.

Anticipated questions from the room
  • "Why Gmail-only?" — One fully working provider proves the vendor-neutral design end-to-end. Outlook rides the same contracts; its remaining work is live-API quirks, not architecture.
  • "Why not guarantee exactly-once delivery?" — It's impractical across networks. We choose availability and make duplicates cheap to detect with a fingerprint. An honest promise beats a false one.
  • "Why poll when push exists?" — Push pings can be forged, dropped, or arrive out of order. Polling from a durable bookmark is the reliable engine; push just shortens latency by waking it.
  • "What's the biggest risk?" — The contract surface. Once published it can't change without breaking consumers — which is exactly why we freeze it before building, and why V1 is "not ready" until it's right.
  • "Is the deferred work risky?" — No. Each deferral is either already designed-for or safe to add later without breaking anyone, because we own all the implementations today.
