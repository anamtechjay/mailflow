mailflow

A reusable library that turns a live email inbox into clean, structured, de-duplicatable events for the app that plugs into it.

One sentence: mailflow watches an inbox, and on every new email it fetches, opens, cleans, and hands a tidy structured record to your app — reliably, exactly once you'd want it, with the messy parts (auth, throttling, duplicates, broken mail) handled for you.

Mental model — an automated mailroom: a letter arrives → the clerk is pinged → the clerk fetches the letter using a bookmark (not the ping) → opens it, pulls out the useful parts, discards junk → hands a summary card to the department that asked. Everything below is how that mailroom is built.

Architecture at a glance

The one idea that explains everything else: mailflow is a small core of frozen contracts (ports) surrounded by swappable implementations. The core knows the shape of a mailbox provider, a webhook verifier, a content cleaner, a store — but never a specific vendor. Gmail and Outlook are just two implementations of the same ports.

That is also the build philosophy: freeze the contracts first, then build behind them in parallel. A contract is a method signature or a model field that, once V1 ships, consumers build against — changing it later breaks them. So the contracts are locked before any parallel implementation work begins.

Core defines the ports; adapters & stores implement them; the facade wires it together for the consumer.

Why a lead should care: the risk in a library isn't the code that works today — it's the promises. Get the ports right and a new provider, store, or cleaner slots in without touching the core or breaking a single consumer. Get them wrong and every consumer pays for the rewrite. V1's whole job is to lock the right promises.

The pipeline, stage by stage

Each card: what the stage does · the contract it freezes · why it matters (the failure it prevents) · V1 status.

1 · Wake signal & webhook verification

A5~ reduced to Gmail OIDC-JWT

"A new-mail ping arrived — but is it really from Google, and is it safe to act on?"

Contract
WebhookVerifier port → returns identity only (verified subscription/mailbox), never payload trust.
V1 impl
Gmail Pub/Sub OIDC-JWT verification — signature via JWKS, audience, issuer. (Outlook validationToken handshake deferred.)
Why it matters
Push ingestion is internet-facing. Without verification, anyone can forge a "you have mail" ping. A verified ping still only earns a wake — never "fetch this exact ID."

2 · Fetch & cursor (the golden rule)

A1A3B6~ Gmail compliant

"On wake, re-derive what changed from a durable bookmark — never trust the ID inside a ping."

Contract
Cursor is durable, strictly monotonic (commit_if_ahead), and advances on every terminal disposition. Gmail = historyId; Outlook = deltaLink.
Why it matters
Pings can be forged, duplicated, or arrive out of order. The bookmark is the only trustworthy source of "where I stopped," so a crash resumes exactly where it left off — no gaps, no re-scans.
V1 status
Gmail already obeys this (re-derives from historyId) and commits one cursor per page (B6 ✓). The Outlook wake-rewire is deferred.

3 · Size guard — fail closed

B1~ to fix

"If we can't tell how big an email is, assume it's too big and set it aside — before downloading."

Behavior
Unknown / omitted size ⇒ treat as over-limit ⇒ DLQ before fetch. (Today an unknown size becomes 0 and sneaks under the ceiling — the bug.)
Why it matters
"Fail open" on size means an unbounded or unknown payload can be pulled into memory and crash the run. Safe default is to reject, not guess.

4 · Extract fields & thread key

A7✗ to build

"Open the envelope, pull out sender/subject/body/attachments — and the ID that groups a conversation."

Contract
New thread_key field on CleanEmail; maps Gmail threadId / Outlook conversationId, with a subject-normalized fallback.
Seam
Extraction sits behind a port. MimeExtractor.extract_bytes(...) for raw RFC822 (Gmail); other providers implement extract(msg, env) directly (Outlook/Graph).
Why it matters
Without a provider-native thread key, consumers can't reliably tie a reply back to its original — conversation grouping breaks.

5 · Clean — HTML → text

A6B5✗ to build

"Turn an email's HTML into readable plain text — gently by default, aggressively only if asked."

Contract
ContentCleaner port (clean(CleanEmail) -> CleanEmail), wired as a real pipeline stage — not a post-emit afterthought.
Parity (B5)
A shared HTML→text converter runs in both extractors, so an HTML-only email yields non-empty body_text the same way regardless of provider.
Why it matters
V1 is plain-text-only (no HTML sanitizer / renderer). So if HTML-only mail produced blank text, the product would look empty. This stage is what makes the output usable.

6 · Filter

A10~ functions work

"Only hand the consumer the emails they actually want."

Built-in
To / CC / subject matching incl. regex; consumers can inject their own filters.
Today
Filters/cleaners inject as plain callables via the facade (connect(filters=[...], clean_fn=...)). What's left is the generic overrides= seam + named as_filter/as_cleaner decorators (see Extensibility).

7 · Emit event & idempotency

A4~ key not on wire

"Hand the consumer a clean event stamped with a fingerprint so they can spot duplicates."

Contract
idempotency_key surfaced on EmailEvent = (tenant, mailbox, provider_message_id). Wire schema bumps 1.0 → 1.1 (additive).
Delivery
At-least-once, documented honestly. Exactly-once is not promised; duplicates are expected and handled by the key. (Docs that claimed exactly-once are being corrected.)
Why it matters
The emitted event is the public contract. The fingerprint is computed internally already — V1 simply exposes it so consumers don't have to rebuild it.

Cross-cutting concerns

Error taxonomy & routing

A2B3✗ foundational

"Sort every failure into Auth / Permanent / Transient, and react differently to each."

Contract
AuthError · PermanentError · TransientError (subclasses of MailflowError); provider errors re-parented onto them.
Routing
Auth (401) → refresh once, retry · Permanent (403/404/410/decode) → DLQ, no retry · Transient (429/5xx/network) → bounded backoff, then DLQ.
Why it matters
Today a single bare except retries everything by attempt count — so "message gone" (410) and "garbled data" retry forever (a poison loop). This is the keystone: B3 and B4 both depend on it.
The routing this taxonomy unlocks.

Reliability — isolation, backoff, storm containment

B2B4~ partial
DLQ isolation (B2)
One broken/oversized message is set aside alone — it must never crash the batch. Counted exactly once (add_dead_letter() + paired trace). Gap: the fetch stage still lacks per-record isolation.
Backoff + storm (B4)
Retry 5xx; exponential backoff + jitter honoring Retry-After; bounded concurrency cap; and crucially contain an exhausted-retry storm so it can't abort the whole run.
Why it matters
These are the difference between "one bad email" and "the run dies." Today a 429 storm propagates uncaught and takes everything down.

Extensibility & stability policy

A8A10A11~ partial
Overrides (A10)
Generic overrides= mapping to inject any component instance, plus as_filter/as_cleaner decorator sugar — so the features above wire up without hand-building internals.
Token rotation (A8)
SecretProvider gains an on-refresh persistence callback: a rotated OAuth refresh token is saved, or the next run silently breaks. (Multi-tenant/DWD intentionally out of V1.)
Versioning (A11)
Explicit sync-only declaration, provisional/stable port markers, and a version field on config — so a future async family is an addition, not a breaking change.

Observability

~ light in V1

Structured logs, counters, run reports, health checks — enough to operate it.

In V1

Deferred
PII redaction (scrubbing bodies from logs) is post-V1; for now, full bodies simply aren't logged by default.

Speaker notes — anticipated questions
  • "Why Gmail-only?" — One provider proves the provider-agnostic design end-to-end (D1). Outlook is an adapter on the same ports; its remaining work is live-API quirks (expiry clamp, size probe), not architecture.
  • "Why not exactly-once?" — Exactly-once across networks is impractical; we choose availability-first and make duplicates cheap to detect with idempotency_key. Honest contract beats a false promise.
  • "Why poll if there's push?" — Push pings can be forged, dropped, or reordered. Poll/delta from a durable cursor is the reliable engine; push just shortens latency by waking it.
  • "Biggest risk?" — The contract surface (Category A). Once published it can't change without breaking consumers, which is exactly why Phase 0 freezes it before any parallel build.
