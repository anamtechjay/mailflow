# mailflow — library viability audit (multi-agent, adversarially verified)

**Date:** 2026-07-02 · **Branch:** `anam/library` @ `90b6ac5`
**Method:** 11 independent reviewer agents (6 feature deep-dives + 5 cross-cutting: scalability,
security, deployment, edge cases, consumer value), each judging the *code* (not the docs) with
mandatory `file:line` evidence. Every critical/high finding was then re-examined by an independent
adversarial verifier instructed to *refute* it. **Result: 18/18 critical+high findings confirmed,
0 refuted**, plus 44 medium/low findings reported unverified.

> Scope note (per `docs/qa-findings.md` discipline): this is a *product/production viability*
> audit against the full library ambition, not a phase-scope QA pass. Some findings intersect
> already-logged QA items (noted inline where reviewers flagged it, e.g. VR1, I5, OD-1).

## Executive verdict

**The design is right; the delivery guarantees are not yet true.** mailflow's architecture —
one `connect()` front door, provider-agnostic `CleanEmail`, ports for cursor/dedupe/DLQ/blob,
explicit dispositions and traces — is genuinely production-shaped, better documented in-code than
most in-house pipelines, and occupies a real market wedge: *self-hosted Gmail/Outlook ingestion
where mail never touches a third party* (vs Nylas/Unipile SaaS or error-prone DIY SDK code).

But the library's one non-negotiable promise — **no silent mail loss** — is currently violated by
six independent, confirmed, reproducible mechanisms (mid-batch cursor advance, batch-final
historyId stamping, bootstrap cursor re-seed, non-outcome-aware Event Hub checkpointing, dedupe
claims without lease expiry, attempt counters erased on release). The Graph live path additionally
stops ingesting silently within ~6 days because nothing renews subscriptions. A real org would hit
several of these in week one, invisibly, with green health signals.

**Adoption verdict: not-yet for external organizations; adopt-with-caveats for an internal Python
team on GCP running a single replica against mailboxes it owns.** The encouraging part: almost every
confirmed defect is a localized fix (often <20 lines) in an otherwise sound structure — this is
weeks of focused correctness work away from "adoptable for Gmail", not a rewrite.

## Per-area verdicts

| Area | Verdict (one line) |
|---|---|
| **Core pipeline & delivery invariants** | Right architecture; at-least-once is broken 3 ways (all silent loss / infinite retry) — fixes are small and localized. |
| **connect() facade & developer experience** | API shape is a real draw; docs contradict behavior (`on_filtered` tag default), `sqlite:///` state string crashes, Gmail `stream()` hangs silently on bad config. |
| **MIME extraction & attachments** | Fail-closed policy design is good; the MIME walker misclassifies ordinary mail (inline bodies → empty emails, forwarded mail mangled, legacy charsets dead-lettered). |
| **Gmail adapter (live path)** | Poll-authoritative design is correct; two cursor bugs silently lose mail on every restart and any partial-batch failure. |
| **Microsoft Graph adapter (live path)** | Good building blocks, but the live entrypoint never renews subscriptions (halts ≤6 days) and checkpoints past failed messages. One integration layer + two fixes from adoptable. |
| **Stores, persistence, emitters, secrets** | Pleasant for dev/pilot; sqlite dedupe turns crashes into permanent loss, DLQ defaults to a discarded in-memory emitter, pubsub emitter unbuildable from config. Gaps are “adapter missing”, not “design blocks it”. |
| **Scalability & concurrency** | Honest sync design fine for a handful of mailboxes / low tens-of-k msgs/day; live loops already violate single-worker via SDK thread pools; no safe multi-process story. |
| **Security** | Better than POC-typical (no secret leaks, fail-closed caps); blockers are PII-at-rest in the DLQ (full raw mail, world-readable sqlite, unbounded retention) and ReDoS in user-supplied filter regexes. |

| **Real-world edge cases & failure scenarios** | Deliberate-failure paths (oversize, poison, filtered) are well built; routine failures (network blip mid-batch, crash, odd charset) silently lose mail in the flagship Gmail path. |
| **Consumer value & market realism** | Compelling wedge (self-hosted, data custody, clean contract); blocked today by no LICENSE/PyPI, one real provider, mandatory Pub/Sub infra, and no attachment-bytes API. |

## Confirmed critical/high issues (all independently verified)

Each issue below was confirmed by an adversarial verifier that attempted to refute it by reading

### C1. [CRITICAL] Mid-batch transient failure silently loses the message forever (at-least-once broken)
*Area: Core pipeline & delivery invariants*

**Evidence:** src/mailflow/core/pipeline.py:143-150 — _run_stream keeps iterating after _process returns None (non-terminal); pipeline.py:282-293 releases the claim and returns None expecting a later refetch. But the next successful message in the same batch calls commit_if_ahead with a later cursor, moving the bookmark past the failed message. Verified by repro: a one-time TransientError on m1 followed by m2 succeeding leaves m1 never emitted, never dead-lettered, never refetched across subsequent runs. Gmail makes this the common case: every message in a history batch shares the same cursor (src/mailflow/adapters/gmail/provider.py:69,86).

**Impact:** Any 429/5xx/network blip while processing a multi-message batch — routine for Gmail under load — permanently drops that email with zero trace, DLQ record, or metric. Directly contradicts README.md:175's at-least-once claim. Fix: stop processing the stream (break) on a non-terminal disposition, or only commit the highest cursor below the first non-terminal message.

**Verifier notes:** I read pipeline.py (_run_stream 143-150 keeps iterating after a None disposition; _retry_or_dead_letter 282-293 releases the claim and returns None) and confirmed commit_if_ahead is then called with the next successful message's later cursor, moving the bookmark past the failed one. I ran a live repro against the real Pipeline with MemoryProvider: m1 raising TransientError once while m2 succeeds leaves cursor at order 2; five subsequent run_once calls fetch nothing — m1 is never emitted, never dead-lettered (emitted ids ['m2'], dlq 0). Gmail is worse: provider.py:69/86 stamps every message in a history batch with the same latest-historyId cursor, and GmailPubSubRuntime acks after run_once returns normally (transient errors are swallowed inside _process), so there is no redelivery safety net either. The existing test suite only covers the single-message case (test_transient_failure_is_not_terminal_cursor_stays), and README.md:175 does claim at-least-once delivery.

### C2. [HIGH] max_attempts is unreachable: release() erases the attempts counter in both bundled dedupe stores, so poison messages retry forever
*Area: Core pipeline & delivery invariants*

**Evidence:** src/mailflow/core/pipeline.py:286,292 checks attempts >= max_attempts, then calls dedupe_store.release(key); src/mailflow/stores/memory.py:65-67 and src/mailflow/stores/sqlite.py:125-128 both DELETE the claim record on release, wiping attempts. Verified by repro: an always-raising extractor with default max_attempts=3 is still retrying after 10 runs with 0 dead-letters. Existing tests only pass because they use max_attempts=1 (tests/test_pipeline_routing.py:142-145). The DedupeStore port (src/mailflow/core/ports.py:110-115) never states that attempts must survive release.

**Impact:** With the default config, a message that deterministically fails (e.g. an extractor bug, a persistent provider 5xx for one message) is re-fetched and re-processed on every run forever instead of dead-lettering after 3 attempts — burning API quota and, per issue 1, blocking or losing the stream. §8.4 'poison goes to DLQ and cursor moves past it' only works at max_attempts=1.

**Verifier notes:** Traced the pipeline flow: try_claim creates a fresh claim, record_attempt returns 1, and on transient failure _retry_or_dead_letter (pipeline.py:286-293) calls release(), which in both bundled stores (memory.py:65-68 del; sqlite.py:125-128 DELETE) erases the record and its attempts counter, so every run restarts at attempts=1. Reproduced empirically: an always-raising extractor with the default max_attempts=3 produced 0 dead-letters over 10 runs with both InMemoryDedupeStore and SqliteDedupeStore, cursor never advancing. No mitigation exists elsewhere: registry.py offers only these two stores, the DedupeStore port states no attempts-survive-release contract, and DLQ-at-max tests all use max_attempts=1.

### C3. [HIGH] Crash between claim and mark_done permanently loses the in-flight message (no store implements lease expiry)
*Area: Core pipeline & delivery invariants*

**Evidence:** src/mailflow/core/pipeline.py:163-165 treats try_claim=False as a terminal 'duplicate' (cursor then advances at :149-150). src/mailflow/stores/sqlite.py:88-89 ('Lease/TTL expiry is not simulated') and :99-105 persist the claim row with done=0 forever; stores/memory.py:44-45 same. No shipped DedupeStore honors lease_seconds.

**Impact:** A process crash or OOM after try_claim but before emit+mark_done leaves a dead claim on disk (SqliteDedupeStore is the offered persistent single-node store). On restart the message is classified 'duplicate' — never emitted — and the cursor commits past it. Every crash mid-message loses exactly that message. At-least-once under crash/restart requires either lease expiry in a bundled store or the pipeline distinguishing 'claimed but not done' from 'done'.

**Verifier notes:** Verified every link in the chain: pipeline.py:163-165 treats try_claim=False as a terminal 'duplicate' and :149-150 commits the cursor past it; SqliteDedupeStore.try_claim (stores/sqlite.py:99-105) is a bare INSERT OR IGNORE that ignores lease_seconds, so a done=0 row from a crashed run blocks the key forever (docstring at :88-89 admits no expiry; memory.py same). release() only runs on in-process transient exceptions (pipeline.py:292) — a SIGKILL/OOM between claim and emit leaves the claim; on restart the un-advanced cursor re-yields the message, it is classified duplicate, never emitted, never dead-lettered (redrive cannot recover it since no DLQ record exists), and the cursor commits past it. No startup sweep or stale-claim recovery exists anywhere in src/, and facade.py:7 explicitly advertises state="sqlite:///mf.db" "for restart-safety" — the exact mode where this bites (the in-memory store is immune since its state dies with the process). docs/qa-findings.md C2 defers lease expiry only as a concurrency concern; this single-node crash-loss framing is not logged. Minor nuance: a crash after emit but before mark_done is safe, so the loss window is claim→emit, but that covers parse/filter/extract/emit — most of the per-message work.

### C4. [HIGH] Documented state="sqlite:///mf.db" resolves to filesystem root and crashes
*Area: connect() facade & developer experience*

**Evidence:** config/state.py:21,30-37 strips only the 9-char "sqlite://" prefix, so "sqlite:///mf.db" becomes path "/mf.db" with blob dir "/attachments". Verified: connect("memory", state="sqlite:///mf.db").fetch_new() raises sqlite3.OperationalError: unable to open database file. This exact string is the example in README.md:60, docs/getting-started.md:71, and docs/mailflow-usage-guide.md:128,325,380.

**Impact:** Every developer who copy-pastes the persistence quickstart gets an immediate crash (or, if running as root/Windows, a database written to the drive root). It also inverts the universal SQLAlchemy convention where sqlite:///x.db means relative path, so even users who "know" the URL form are misled.

**Verifier correction:** Everything stated is accurate (the crash actually occurs at connect(), even earlier than claimed), but severity is high rather than critical: it is a loud, immediate, deterministic crash in a documented opt-in quickstart with a trivial workaround (absolute path), not silent data loss or a security flaw; the write-to-drive-root scenario requires unusual privileges.

**Verifier notes:** Reproduced the exact failure: config/state.py:31 strips only "sqlite://" so the documented "sqlite:///mf.db" becomes "/mf.db", and connect("memory", state="sqlite:///mf.db") raises sqlite3.OperationalError at connect() (stores/sqlite.py:52 opens the connection eagerly) — even before fetch_new(). The string appears verbatim in README.md:60/152, docs/getting-started.md:71, and docs/mailflow-usage-guide.md:128/325/380; no mitigation exists in the facade, registry, or stores, and tests only cover absolute paths so the gap is untested. The convention also inverts SQLAlchemy's sqlite:///relative form as claimed.

### C5. [HIGH] All docs except README still describe filters as dropping mail, but the default on_filtered="tag" delivers matched mail
*Area: connect() facade & developer experience*

**Evidence:** core/pipeline.py:208-232 and facade.py:233 make "tag" the default: a blacklist match is extracted and emitted with disposition="filtered". Verified: connect("memory", filters=[{"kind":"blacklist","domains":["spam.com"]}]) delivers the spam.com email. docs/getting-started.md:87-91 ("which emails reach you"), docs/mailflow-usage-guide.md:161-220,350-368 (every table row says DROP; all real-world recipes), and examples/feature-explorer-v2.html:380-435 ("every sender @spam.com is dropped") contain zero mentions of on_filtered (grep confirms).

**Impact:** An adopter building an invoice bot or support-desk intake from the usage-guide recipes will process spam, newsletters, and out-of-scope mail as if filtered, because their loop never checks disposition. Worse, combined with fields= projection the tag is invisible unless the user thinks to request "disposition" (facade.py:87-88 projects only named fields).

**Verifier notes:** I reproduced the claimed behavior with the venv interpreter: connect("memory", filters=[{"kind":"blacklist","domains":["spam.com"]}]) delivers the spam.com email with disposition="filtered" (facade.py:233 defaults on_filtered="tag"; core/pipeline.py:208-232 falls through to extract+emit on a filter match), and with fields=["subject","from"] the projected dict contains no disposition/matched_filter key at all (facade.py:87-88 projects only the named fields), so the tag is invisible. Grep confirms on_filtered appears only in README.md; docs/getting-started.md ("which emails reach you"), docs/mailflow-usage-guide.md §5 (every builtin table row says DROP, custom-filter docs say "False = drop", all §5.4 recipes), and examples/feature-explorer-v2.html ("every sender @spam.com is dropped BEFORE the body is parsed") all still describe the old drop semantics with zero mention of on_filtered or disposition-checking. Commit 90b6ac5 updated only the README, leaving the primary usage guide contradicting actual behavior; this is not logged in docs/qa-findings.md.

### C6. [HIGH] Usage-guide "only invoices" recipes are logically inverted — the subject filter drops the invoices
*Area: connect() facade & developer experience*

**Evidence:** filters/deterministic.py:135-139: SubjectFilter DROPS on pattern match. docs/mailflow-usage-guide.md:218-219 ("# only invoices, exclude newsletters: filters=[{\"kind\": \"subject\", \"patterns\": [\"(?i)invoice\"]}, ...]") and :362-367 ("Invoice bot: only known senders + invoice subjects") use it as a keep rule. Verified: with on_filtered="drop", an email with subject "Invoice 42" is suppressed — the recipe deletes exactly the mail it wants.

**Impact:** A developer following the canonical example ships a bot that discards every invoice. There is also no built-in keep-only-matching-subject filter, so the advertised use case is only achievable via a custom lambda — a capability gap the docs paper over.

**Verifier correction:** Accurate as stated, with one nuance: under the library default on_filtered="tag", invoices are not silently deleted — they are delivered tagged disposition="filtered" (and newsletters/other mail also flow through), so the recipe fails as "everything arrives, invoices mis-tagged as junk"; the outright-discard failure requires on_filtered="drop", which the reviewer correctly conditioned on.

**Verifier notes:** SubjectFilter.evaluate (src/mailflow/filters/deterministic.py:135-139) returns FilterDecision.drop on pattern match, and registry.py:68 maps {"kind": "subject"} to it with no inversion; FILTER_KINDS has no keep-only subject variant. The guide's own §5.1 table correctly documents subject as "DROP if subject matches a regex", yet the §5.4 recipe ("only invoices, exclude newsletters", docs/mailflow-usage-guide.md:218-219) and the §13 Invoice-bot recipe (:362-367) use it as a keep rule — and OnlySenderFilter returns uncertain (not KEEP) for allowed senders, so the subject filter does run and flags every invoice. With on_filtered="drop" the invoice is terminally suppressed (cursor advances, marked done — unrecoverable skip); under the default "tag" (pipeline.py:208-232) it is still delivered but marked disposition="filtered", so the recipe is inverted either way, and the only keep-on-subject path is the custom lambda the guide shows in §5.3.

### C7. [HIGH] Gmail stream() hangs forever on any startup failure — errors die in a daemon thread with no stop API
*Area: connect() facade & developer experience*

**Evidence:** facade.py:182-185 spawns the live loop as a daemon Thread and then blocks on queue.items(); emit/callback.py:58-64 blocks on q.get() until a sentinel that only close() sends — and nothing calls close() when the thread dies. Any exception in run_service (missing google SDK extra, bad refresh token, Pub/Sub permission error) kills the thread; the consumer's for-loop blocks indefinitely.

**Impact:** The most common first-run failures (forgot pip install "mailflow[gmail]", wrong credentials) present as "no mail arrives" plus a stderr traceback that is easy to miss under supervisord/systemd — a production service that looks alive but ingests nothing. There is also no way to gracefully stop a stream() other than killing the process.

**Verifier correction:** The hang is real for any failure inside run_service (bad/revoked refresh token, scope mismatch, Pub/Sub permission/network errors, missing google-cloud-pubsub with httpx/google-auth transitively present), and there is no stop API. However, "forgot pip install mailflow[gmail]" and unset env-var credentials fail fast at connect() with ImportError/KeyError via the eagerly-built gmail fetcher, so those specific first-run cases do not hang.

**Verifier notes:** Verified in facade.py:182-185 that stream() spawns the live loop as a bare daemon thread and blocks on QueueEmitter.items(), which waits for a sentinel only close() sends (emit/callback.py:58-67) — and nothing in src/ ever calls close(). run_service (adapters/gmail/live.py:199-286) has no error funnel: any exception (invalid/revoked refresh token during verify_oauth_scopes, AuthError on missing scopes, missing google-cloud-pubsub, watch bootstrap or Pub/Sub permission errors) kills the thread with only a stderr traceback, leaving the consumer's for-loop blocked forever; Mailflow also exposes no stop/close API. One correction: two headline examples are wrong — a wholly-missing gmail extra and an unset env:// secret fail fast at connect() because _build_gmail_fetcher eagerly imports httpx/google.oauth2 and resolves secrets (facade.py:292-296, 306-331).

### C8. [CRITICAL] Text bodies with explicit Content-Disposition: inline are misclassified as attachments, producing empty body_text/body_html
*Area: MIME extraction & attachments*

**Evidence:** mime.py:196 sets is_inline_media = disp == "inline" or cid is not None; the body branches at mime.py:198-203 require `not is_inline_media`, so a text/plain or text/html part carrying the (RFC-2183-legal, very common) explicit `Content-Disposition: inline` header is routed to the attachment path at mime.py:205. Verified live: a multipart/alternative message with inline-disposition text parts extracts body_text='' , body_html='' and two nameless text/* 'inline attachments'. Same failure for senders that put Content-ID on body parts (verified: body became an inline attachment).

**Impact:** Mail from mutt, Mailman lists, and many transactional senders that emit explicit inline dispositions on body parts is delivered to consumers as an empty email whose body bytes sit in the blob store as anonymous attachments. Downstream apps (ticketing, CRM ingestion) silently lose the message content.

**Verifier notes:** Reproduced live against src/mailflow/extract/mime.py using the venv: a multipart/alternative with Content-Disposition: inline on text parts, a Content-ID-bearing text/plain body, and a mutt-style single-part inline message all extract body_text='' / body_html='' with the text parts emitted as nameless inline attachments (lines 195-205 route any disp=='inline' or Content-ID part away from the body branches). No mitigation exists: the HTML->text fallback (mime.py:227) and the A6 cleaner (clean.py:49) only backfill from body_html, which is also empty, and MimeExtractor is the default extractor at every consumer entrypoint (facade.py:268/332, builder.py:60, redrive.py:107). No test or golden fixture covers this shape (qa-findings I1 even flags the inline-CID branch as never exercised), and with a non-empty legacy allowlist lacking text/plain such mail would DLQ outright.

### C9. [HIGH] message/rfc822 attachments (forwarded-as-attachment email) are lost and their inner parts leak into the outer message
*Area: MIME extraction & attachments*

**Evidence:** mime.py:187-189: msg.walk() descends into message/rfc822 containers, and the container itself hits `if part.is_multipart(): continue`, so the attached .eml is never recorded as an attachment. Verified live: outer message with an attached forwarded email produced body_html='<p>INNER HTML BODY</p>' (the inner message's body) and attachments=[('inner.pdf','application/pdf')] (the inner message's attachment), while 'report.eml' vanished.

**Impact:** Phishing-report and support workflows (forward-as-attachment is the standard reporting mechanism) get a CleanEmail where the malicious inner PDF is attributed to the reporter's own message, the inner HTML overwrites the outer body, and the forwarded email itself is unrecoverable. Content confusion across a trust boundary.

**Verifier correction:** Accurate except one detail: the inner HTML does not overwrite an existing outer HTML body — body assignment is first-match-wins, so the inner body_html leaks only when the outer message has no HTML part of its own (body_text remains the outer's). The attachment loss/mis-attribution is unconditional.

**Verifier notes:** Reproduced live against src/mailflow/extract/mime.py (_walk_body, lines 187-189) on both the legacy and policy paths: an outer message with an attached forwarded email yields attachments=[('inner.pdf','application/pdf')] (the inner message's attachment attributed to the outer), body_html='<p>INNER HTML BODY</p>' (the inner message's HTML), and 'report.eml' appears in neither attachments nor stripped_attachments — message/rfc822 is is_multipart()==True so the container is skipped while walk() descends into it. No mitigation exists anywhere: grep finds zero rfc822/nested-message handling in src/ or tests/, and docs/qa-findings.md and the plans never mention it (not a logged/deferred item). One nuance: the inner HTML "fills" body_html only when the outer message lacks its own HTML part (first-match-wins), and body_text stays the outer's — so "overwrites the outer body" is slightly overstated, but the trust-boundary confusion (inner malicious PDF attributed to the reporter, forwarded .eml unrecoverable, inner attachment run through the outer's policy/scanner/blob store) holds exactly as claimed.

### C10. [HIGH] Unknown/bogus charset on a text part raises uncaught LookupError; legitimate mail is retried then dead-lettered
*Area: MIME extraction & attachments*

**Evidence:** mime.py:199 and mime.py:201 call part.get_content(), and envelope.py:85 calls body.get_content() for the snippet; with policy=default an unknown charset (e.g. charset="unknown-8bit", "chinesebig5") raises LookupError (verified live). Pipeline treats it as transient (pipeline.py:200-201) so a deterministic parse failure burns max_attempts retries then DLQs (pipeline.py:282-295).

**Impact:** Real-world mail routinely carries junk charset labels (legacy MTAs, misconfigured senders, most spam that should instead be filtered). Every such message is retried pointlessly and then quarantined, so operators see legitimate mail piling up in the DLQ with LookupError instead of a best-effort decoded body.

**Verifier correction:** The defect is real but the claimed outcome ("retried max_attempts then dead-lettered") understates it: with the shipped memory/sqlite dedupe stores, release() deletes the claim record so attempts reset to 1 on every retry — the message NEVER dead-letters. It is either retried indefinitely (if it is the newest message, pinning the cursor) or silently lost with no DLQ record and no trace once any later message succeeds and commit_if_ahead moves the cursor past it. Also note the envelope parser (envelope.py:85) raises before filters run, so even spam that a filter would drop hits this path. Root cause stands: unknown/bogus charset labels (e.g. charset=unknown-8bit) raise uncaught LookupError from get_content(), and this deterministic parse failure is classified as transient instead of being decoded best-effort or treated as permanent.

**Verifier notes:** Verified live with the venv: message_from_bytes(policy=default) + get_content() raises LookupError("unknown encoding: unknown-8bit") at mime.py:199/201 and envelope.py:85 (the envelope parser raises too, so the failure hits BEFORE filters — even filterable spam trips it). No charset handling exists anywhere in src/ (grep for LookupError/charset/UnicodeDecodeError found nothing), and pipeline.py:200-201 routes it through the generic except Exception → _retry_or_dead_letter. Ran the real consumer path (connect("memory", seed=...)) end-to-end: the message loops forever without ever DLQing, because both InMemoryDedupeStore.release (stores/memory.py:65-68) and the sqlite release (stores/sqlite.py:125-128) DELETE the claim row, resetting attempts to 1 each run so attempts never reaches max_attempts; and once a later message succeeds, commit_if_ahead advances the cursor past the poison message, silently dropping it with no DLQ record at all.

### C11. [CRITICAL] Batch-final historyId stamped on every message: any mid-batch failure or crash permanently skips mail
*Area: Gmail adapter (live path)*

**Evidence:** src/mailflow/adapters/gmail/provider.py:69 builds one cursor from the diff's final historyId (`new_cursor = Cursor(value=latest, order=int(latest))`) and stamps it on every yielded RawMessage (provider.py:85). src/mailflow/core/pipeline.py:149-150 commits that cursor after EACH terminal disposition, so the first success in a batch advances the stored cursor past ALL messages in the diff.

**Impact:** history.list returns [A, B]. A fails transiently (disposition None, claim released, pipeline.py:292-293); B emits and commits cursor=latest. A is now behind the cursor: Pub/Sub redelivery and the 15-min sweep both diff from `latest`, so A is never fetched again — silently lost, no DLQ record. Same loss if the process crashes after the first message of an N-message batch commits. On a busy mailbox with multi-message diffs this is a routine, undetectable data-loss path.

**Verifier notes:** Verified all cited code: provider.py:69/85 stamps one batch-final historyId cursor on every RawMessage; pipeline.py:149-150 commits it on each terminal disposition, so any success in a multi-message diff advances the stored cursor past a sibling that failed transiently (pipeline.py:292-293 returns None/releases claim, relying on cursor non-advancement for retry). Checked all recovery paths and found none: fetch (provider.py:57) prefers the stored cursor over a redelivered notification's historyId, and the 15-min sweep (bootstrap.py:48-54) also diffs from the stored cursor, so the skipped message is never refetched and gets no DLQ record. The project's own docs/qa-findings.md VR1 documents this exact bug class for the Graph adapter but incorrectly claims Gmail uses a per-message cursor — git history shows the batch-final cursor has been there since the initial commit.

### C12. [CRITICAL] bootstrap_watches re-seeds the cursor to the current historyId on every restart, skipping all mail received while down
*Area: Gmail adapter (live path)*

**Evidence:** src/mailflow/adapters/gmail/bootstrap.py:24-27 unconditionally calls commit_if_ahead with the fresh watch's historyId; commit_if_ahead overwrites whenever the new order is strictly greater (src/mailflow/stores/memory.py:25-31, sqlite.py:67-82). users.watch returns the mailbox's CURRENT historyId, which is always ahead of a cursor stored before downtime. run_service defaults start_watch=True (live.py:211, 242-248) and the facade uses that default (facade.py:388).

**Impact:** Deploy restarts the service after a 1-hour outage; 40 emails arrived meanwhile. On startup the cursor jumps from the pre-outage historyId to now, so the first diff (and the safety-net sweep) start after those 40 messages. All downtime mail is silently skipped on every single restart — the opposite of the durable-cursor promise.

**Verifier notes:** Verified the full chain: bootstrap_watches (src/mailflow/adapters/gmail/bootstrap.py:24-27) unconditionally commits the fresh users.watch historyId with no "only seed if no cursor exists" guard, and both cursor stores' commit_if_ahead accept any strictly-greater order (memory.py:25-31, sqlite.py:67-82) — after downtime with mail, the watch's current historyId is always greater than the durably stored cursor, so it overwrites forward. run_service defaults start_watch=True and the facade uses that default (live.py:211/242-248, facade.py:386-393), and bootstrap runs BEFORE the consume loop, so recovery paths cannot save the gap: GmailProvider.fetch diffs from the STORED cursor (provider.py:57), meaning redelivered Pub/Sub notifications from the downtime window and the safety-net sweep (bootstrap.py:48-56) both diff from "now" and return nothing. This defeats the facade's own advertised restart-safety ('state="sqlite:///mf.db"' for restart-safety, facade.py:7); tests only cover first-seed (test_gmail_watch_lifecycle.py) and docs/qa-findings.md has no entry for this. Only nuance: with the default in-memory cursor store the cursor is lost on restart anyway, so the bug specifically bites the documented durable-cursor configuration — which is exactly the configuration the finding targets. ### C18. [HIGH] Delta sweep stamps every message with the FINAL deltaLink, so a mid-sweep crash or failure permanently skips the remainder
*Area: Microsoft Graph adapter (live path)*

**Evidence:** src/mailflow/adapters/graph/provider.py:100-113: sweep drains all pages first (client.py:80-97 buffers the entire delta result in memory), then yields each message with cursor=Cursor(value=new_delta, ...) — the post-sweep token. The pipeline commits the cursor after each terminal message (core/pipeline.py:148-150), so message #1 already persists the final deltaLink.

**Impact:** A 'missed' recovery sweep returns 500 messages; the process dies at #200. The stored cursor is already the post-sweep token, so on redelivery the sweep resumes past all 500 — messages 201-500 are never fetched again. The catch-up mechanism itself creates a permanent-loss window, defeating its purpose.

**Verifier notes:** Verified all three cited code sites: client.delta_sweep (client.py:75-95) drains all pages and returns only the final deltaLink; GraphProvider.sweep (provider.py:100-115) stamps every yielded message, including the first, with Cursor(value=new_delta, order=incrementing); Pipeline._run_stream (pipeline.py:148-150) commits the cursor after each terminal message, so the final deltaLink persists after message #1. On restart the stored value startswith("http") and is used as the resume token (provider.py:95-99), which by Graph delta semantics returns only post-sweep changes — messages unprocessed at crash time are never re-fetched, and no mitigation exists (dedupe only prevents duplicates; the sweep is the sole recovery path for 'missed' lifecycle events per composition.py:83-90; no tests cover delta_sweep). The bug is actually slightly worse than stated: even a non-crash transient failure on one sweep message loses it, because the next message commits the same final deltaLink with a higher order, defeating the return-None retry hold at pipeline.py:293.

GraphProvider.message_size also under-guards: it sums attachment metadata + body length (provider.py:118-124) but bytes are never actually downloaded anyway.
  - Impact: A consumer that works against the Gmail/MIME adapter (attachments retrievable via storage_ref) silently gets empty storage_ref/content_hash on Graph — attachment-dependent workflows (invoice ingestion, compliance archiving) break only on Microsoft tenants, with no error.
- **[low] (graph-adapter)** Without a subscription manager every notification is attributed to folder 'inbox', and connect() does not expose graph at all
  - Evidence: src/mailflow/adapters/graph/provider.py:48-55: _stream_for falls back to StreamRef(mailbox, folder="inbox") when stream_resolver is None — which is exactly the run_service configuration (composition.py:63-66, live.py:199-210). facade.py:236 states 'graph is wired but not exposed here yet', so the documented connect() facade cannot build a Graph pipeline.
  - Impact: Sent-items subscriptions (default folders include 'sentitems', config.py:33) produce CleanEmails with folder='inbox' and wrong cursor stream keys; adopters also cannot use the advertised one-call connect() API and must hand-assemble run_service plus their own provisioning.
- **[medium] (stores-emit)** LocalBlobStore crash mid-write leaves a permanently truncated attachment that retries refuse to heal
  - Evidence: put_stream writes directly to the final path, and the existence check short-circuits retries (src/mailflow/stores/local_blob.py:17-27); the code's own NOTE admits a truncated blob "sits at path and the dedupe guard above makes a retry skip it rather than self-heal — reads are not hash-verified".
  - Impact: A crash or disk-full during attachment write leaves a corrupt blob under its content-hash ref; every future occurrence of the same attachment (content-addressed) is deduped against the corrupt file, and open() serves the truncated bytes forever. Fix is the standard temp-file + os.rename, ~5 lines.
- **[medium] (stores-emit)** pubsub emitter is config-valid but unbuildable, and drops the event's ordering_key
  - Evidence: "pubsub" is in EMITTER_KINDS (src/mailflow/registry.py:47) so configs validate, but build_emitter("pubsub") raises NotImplementedError (src/mailflow/registry.py:93-99). PubSubEmitter.publish passes tenant/schema_version/canonical_id attributes but not ordering_key (src/mailflow/emit/pubsub.py:33-40), even though the pipeline stamps ordering_key=mailbox on every event (src/mailflow/core/pipeline.py:248); it also blocks on future.result() per message — serial, no batching or retry settings.
  - Impact: An org writing emitter: {kind: pubsub} in config passes validation and fails at build time with NotImplementedError — they must hand-wire build_pubsub_emitter via overrides. When they do, per-mailbox ordering that the event model promises is silently lost at the Pub/Sub boundary (docs/qa-findings.md defers ordering to Plans 2/4, but nothing warns the adopter), and throughput caps at one synchronous publish per email. Adapter-fixable, not design-blocked: the Emitter port is fine.
- **[medium] (stores-emit)** SecretProvider is env-only and silently treats any bare string as a literal secret
  - Evidence: EnvSecretProvider returns any ref without "://" verbatim (src/mailflow/secrets/env.py:25-28); _KNOWN_SCHEMES contains only env:// (env.py:13-14). No GSM/Key Vault/AWS SM provider exists anywhere; gmail/graph configs correctly carry *_ref fields (src/mailflow/adapters/gmail/config.py:27-28).
  - Impact: A user who writes client_secret_ref: "GMAIL_CLIENT_SECRET" (forgetting env://) has the literal string "GMAIL_CLIENT_SECRET" used as the OAuth secret — auth fails with an opaque provider error, not a config error. The pass-through also invites putting real secrets in config files. Port shape (get(ref) -> str) makes cloud providers an easy extension — adapter missing, not design-blocked — though the port has no caching/rotation hook, which the Gmail token-refresh path currently doesn't need.
- **[low] (stores-emit)** StagesEmitter drops are recorded and counted as "emitted"
  - Evidence: StagesEmitter.emit returns None when a stage drops the email (src/mailflow/emit/stages.py:41-45), but the pipeline ignores the emitter's return value, then marks done and records Disposition.emitted (src/mailflow/core/pipeline.py:252-257).
  - Impact: An org using stages/clean_fn to drop mail sees RunReport.emitted include emails that never reached their sink; reconciling "pipeline says 100 emitted" against "queue received 88" during an incident wastes time. Deliberate layering per the module docstring, but the count discrepancy is undocumented.
- **[low] (stores-emit)** sqlite stores lack lifecycle and hygiene: no close(), three connections per file, NULL-duplicable UNIQUE key in SqliteEmailStore
  - Evidence: SqliteCursorStore/SqliteDedupeStore/SqliteDeadLetterStore each open their own connection (src/mailflow/stores/sqlite.py:52,94,137) and none has close() (SqliteEmailStore does, persistence/sqlite_store.py:223). SqliteEmailStore keys dedupe on canonical_id TEXT UNIQUE (persistence/sqlite_store.py:18) — SQLite UNIQUE permits unlimited NULLs, and save() inserts e.get("canonical_id") which can be None (persistence/sqlite_store.py:74-93); no index on thread_key despite GROUP BY/lookup queries (persistence/sqlite_store.py:113-125,150-168).
  - Impact: Long-running apps leak file handles and cannot cleanly release the db for backup; an event missing canonical_id is stored repeatedly on redelivery (duplicates in the inbox demo); thread queries degrade linearly as the table grows. All polish-tier for the current demo-store role.
- **[medium] (scalability)** No per-mailbox parallelism; every message costs sequential blocking HTTP, capping one worker at ~1-3 msgs/s
  - Evidence: run_once iterates streams strictly sequentially (core/pipeline.py:139-141); per message the Gmail path does messages.get format=raw (client.py:151-156, full body over one httpx call with 30s timeout) and the emitter blocks per event on future.result() (emit/pubsub.py:40). Retry backoff sleeps inline (client.py:38-46), stalling the entire worker.
  - Impact: One mailbox receiving a 25MB attachment or hitting a 429 backoff (sleeps up to ~8s+ inline) freezes ingestion for all other mailboxes on the handle. At 100 mailboxes with normal morning bursts, delivery latency stretches to minutes; 1M msgs/day (≈12/s sustained, 50/s peak) is ~10-40x beyond a single worker. Lifting this needs per-mailbox worker fan-out (mailbox = natural ordering unit) plus non-blocking/batched publish.
- **[medium] (scalability)** No backpressure on the stream() path: QueueEmitter is unbounded
  - Evidence: QueueEmitter uses queue.Queue() with no maxsize (emit/callback.py:41-45); Mailflow.stream() runs the live loop on a daemon thread and yields from that queue (facade.py:182-185). Nothing bounds it or signals the producer.
  - Impact: A consumer iterating mf.stream() slower than ingestion (e.g. each email goes through an LLM call) accumulates full CleanEmail objects — bodies included — in RAM without limit until OOM. The on_email/CallbackEmitter path is inverse: a slow callback stalls the Pub/Sub callback thread; with no flow_control configured (live.py:190) up to 1000 messages lease-extend in the subscriber until the default max lease lapses and redelivery piles up.
- **[medium] (scalability)** Large messages are held in memory ~4-5x, and DLQ'd messages are base64-inflated into SQLite rows
  - Evidence: get_message_raw parses the whole JSON response (base64 body ≈1.33x message size) into a dict (gmail/client.py:151-156), then _b64url_decode materializes the full decoded bytes (gmail/provider.py:72-73), RawMessage holds them, and on dead-letter pipeline.py:368 re-encodes the entire raw_bytes to base64 into the DeadLetterRecord, which SqliteDeadLetterStore stores as one row and list_pending loads back wholesale (stores/sqlite.py:142-159).
  - Impact: With the default max_message_bytes=50MB (pipeline.py:61), one message can transiently cost 150-250MB of RAM — multiplied by the unintended 10-way Pub/Sub callback concurrency this is multi-GB. A burst of oversized/poison messages bloats mailflow.db by ~67MB per DLQ record, and an operator redrive that calls list_pending() with no limit loads the entire DLQ into memory.
- **[low] (scalability)** The 'async family is additive, not breaking' promise is technically true but architecturally empty
  - Evidence: ports.py:27-29 declares SYNC_ONLY and promises an additive async family; every port is a sync def, the Pipeline is straight-line sync (pipeline.py:136-201), transports construct sync httpx.Client (gmail/live.py:149-158, graph/live.py:74-83), stores are sync sqlite, and both consume loops are blocking (gmail/live.py:172-196, graph/live.py:102-170).
  - Impact: Adding AsyncMailboxProvider/AsyncEmitter/etc. indeed breaks nothing — but it reuses nothing: the orchestrator, retry/backoff logic, both adapters, and all stores must be reimplemented, and consumers get zero migration path (a sync FilterChain or store cannot be awaited). Adopters betting on 'async is coming additively' should understand it is a parallel second library, not an upgrade of this one; the frozen sync-only port signatures are what guarantee that.
- **[medium] (security)** SQLite state files and local attachment blobs are written with default umask permissions (typically world-readable)
  - Evidence: stores/sqlite.py:52,94,137 call sqlite3.connect with no chmod; stores/local_blob.py:14 (os.makedirs) and :24 (open(path,'wb')) persist decoded attachment bytes with default perms. state="sqlite:///mf.db" wires LocalBlobStore automatically (config/state.py:37-42). Contrast adapters/gmail/rotation.py:28-31, which correctly enforces 0600.
  - Impact: On a shared host, any local user can read cursor/dedupe metadata (mailbox addresses, message ids), every persisted attachment payload, and — if the DLQ store is enabled — full raw emails. The library already knows how to do this right (rotation sink), so the inconsistency will surprise security reviewers at adopting orgs.
- **[medium] (security)** Gmail provider downloads and decodes full message bytes before the pipeline's size guard, defeating the documented fail-closed B1 invariant
  - Evidence: adapters/gmail/provider.py:72-73 calls get_message_raw and base64-decodes the entire payload for every history id inside fetch(); the size guard that claims to run "BEFORE downloading/decoding bytes" only executes afterwards in core/pipeline.py:169-184. Both the base64 str and decoded bytes coexist in memory (~2.3x message size).
  - Impact: max_message_bytes cannot prevent memory spend on Gmail: a burst of near-50MB messages (Gmail's own ceiling) is fully downloaded and decoded regardless of a lower configured cap, enabling memory-pressure DoS on small workers and wasting egress on mail that is then dead-lettered as oversized.
- **[low] (security)** OData filter injection in get_message_by_internet_id: single quotes in a sender-controlled internetMessageId are not escaped
  - Evidence: adapters/graph/client.py:62 builds quote(f"internetMessageId eq '{internet_id}'"); urllib quote percent-encodes the quote for the URL but Graph decodes it back, so a Message-ID like x' or subject ne 'y rewrites the OData filter (OData escaping requires doubling quotes). Currently only reachable if a consumer calls provider.submit_internet_id (adapters/graph/provider.py:38,136) — no production caller exists yet.
  - Impact: Once the internet-id fallback is wired (it is the module's stated purpose), a sender who controls their own Message-ID can broaden the fallback query so the pipeline ingests the wrong message from the victim mailbox (items[0] of an attacker-shaped filter), corrupting identity/dedupe or surfacing unintended mail to downstream consumers.
- **[low] (security)** GmailWebhookVerifier is unwired in the shipped push path and, by default, does not pin the pushing service account
  - Evidence: runtime.py:33 calls parse_pubsub_message(message.data) with no verifier/headers, so the A5 verifier (adapters/gmail/webhook.py) is dead code in the shipped flow; webhook.py:59,77 show allowed_emails defaults to None, meaning any Google-signed OIDC token bearing the configured audience passes — an attacker's own push subscription (their service account, your audience string) satisfies iss/aud checks.
  - Impact: Pull mode is safe today (subscriber credentials authenticate the feed). But an adopter who deploys push mode and wires the verifier as-is still accepts forged wake signals (quota-draining history sweeps); and an adopter who deploys push without reading the code gets no verification at all, since nothing in the library connects the verifier to a request path.
- **[low] (security)** Graph clientState tripwire defaults to the well-known constant "mailflow"
  - Evidence: adapters/graph/config.py:37 sets client_state: str = "mailflow"; subscriptions are created with it (adapters/graph/subscriptions.py:62) and notifications are only accepted when it matches (adapters/graph/notifications.py:61,92). No entropy requirement or startup warning exists.
  - Impact: The constant-time comparison is meaningless when the compared value is a public default from the source code: anyone able to inject events into the Event Hub (misconfigured shared namespace, overly broad SAS key) can forge notifications naming arbitrary tenant mailboxes, which the app-only Graph token will then happily fetch (provider.py:127-140).
- **[low] (security)** EnvSecretProvider's literal pass-through invites plaintext secrets in config and credentials dicts
  - Evidence: secrets/env.py:28 returns any scheme-less ref verbatim as the secret. The *_ref-named fields (e.g. client_secret_ref, facade.py:322-323) therefore silently accept the actual secret value, and everything keeps working.
  - Impact: A developer who pastes the real client secret into credentials={"client_secret_ref": "GOCSPX-..."} gets no error and no signal that the value belongs in the environment — those dicts routinely end up in config files and version control, leaking long-lived OAuth credentials.
- **[medium] (deployment)** Serverless (Lambda / Cloud Functions) deployment is architecturally blocked with no per-event entrypoint
  - Evidence: Both entrypoints block indefinitely (gmail/live.py:190-196 future.result(); graph/live.py:164-170 receive_batch) and depend on in-process daemon-thread schedulers (gmail/live.py:259-276). fetch_new() raises for gmail — the handle is built with run_once=None (facade.py:163-164, 297-301) — and the only store kinds are memory/sqlite/local (registry.py:48), none usable from stateless function instances.
  - Impact: Teams standardized on Pub/Sub-push-to-Cloud-Functions or Lambda cannot adopt mailflow at all; the building blocks (provider.submit + pipeline.run_once, runtime.py:31-40) exist but no supported per-event entrypoint or shared state store is shipped.
- **[medium] (deployment)** No health/readiness HTTP surface and no graceful-shutdown handling for container platforms
  - Evidence: health() is only a Python method on the handle (facade.py:198-206) and its blob check is a non-probing isinstance test (core/observability.py:160-161); no module serves it over HTTP and nothing binds $PORT. The gmail loop handles only KeyboardInterrupt (gmail/live.py:193-196); the graph loop handles no signal at all (graph/live.py:164-170). No SIGTERM handler exists anywhere in src/ or scripts/.
  - Impact: On Cloud Run (services require a $PORT listener) and Kubernetes (liveness/readiness probes), every adopter must write a bespoke HTTP wrapper and signal handler; a hung consume loop passes whatever ad-hoc liveness check they invent, and SIGTERM produces abrupt kills and redelivery churn instead of a drained shutdown.
- **[medium] (deployment)** Multiple replicas are unsafe: no shared state store and no leader election, and the constraint is undocumented
  - Evidence: STORE_KINDS = {"memory", "sqlite", "local"} (registry.py:48); SqliteCursorStore/SqliteDedupeStore open a local file with a per-process threading.Lock (stores/sqlite.py:50-55, 92-97). run_service unconditionally re-runs bootstrap_watches per instance (gmail/live.py:242-248). No leader-election or distributed-lock code exists.
  - Impact: A team that scales a K8s Deployment to 2 replicas gets two independent cursor/dedupe files: overlapping Gmail history fetches emit duplicate CleanEmails downstream and both replicas fight over the watch — violating the library's own dedupe promise without any warning in README/INSTALL.
- **[medium] (deployment)** Ops packaging gaps: no CLI entrypoint, no py.typed, no SQLite schema versioning, unbounded claims-table growth
  - Evidence: pyproject.toml has no [project.scripts] and no license/readme metadata; src/mailflow/py.typed does not exist despite the mypy-strict codebase. SQLite stores use bare CREATE TABLE IF NOT EXISTS with no schema-version table or migration path (stores/sqlite.py:20-44). SqliteDedupeStore.mark_done ignores its ttl_seconds argument and nothing ever prunes done claims (stores/sqlite.py:119-123), so mailflow.db grows one row per message forever.
  - Impact: Ops teams must write a Python driver script for every deployment (systemd ExecStart, container CMD); a future column change breaks existing .db files with no upgrade story; and a long-running mailbox at modest volume accretes millions of claim rows, degrading the dedupe hot path and bloating disk.
- **[medium] (edge-cases)** Stale-historyId recovery silently skips the entire downtime gap with zero logging, metric, or DLQ record
  - Evidence: src/mailflow/adapters/gmail/provider.py:63-67 catches StaleHistoryError, calls _reseed (provider.py:91-99) to jump the cursor to the current historyId, and returns — no log line, no trace, no RunReport entry anywhere in the module (the module has no logger at all). The maintenance scheduler likewise swallows every renewal/sweep exception unlogged (src/mailflow/adapters/gmail/scheduler.py:26-27).
  - Impact: Scenario 5 first half: after two weeks of downtime the stored historyId is expired; on restart every email received during the outage is skipped and the operator gets no signal whatsoever that a gap occurred — the run looks healthy (fetched=0).
- **[medium] (edge-cases)** Gmail downloads the full raw message before the size guard runs, and an oversize/attachment-cap DLQ then re-persists ~1.33x the bytes as base64
  - Evidence: src/mailflow/adapters/gmail/provider.py:72-73 fetches messages.get(format=raw) and decodes it for every history id; the size guard only runs later against msg.size_bytes (pipeline.py:172, provider.py:101-102 message_size just echoes the already-downloaded size), contradicting the stated invariant "size guard ... BEFORE downloading/decoding bytes" (pipeline.py:169-171). The DLQ record then stores the whole message as raw_b64 (pipeline.py:368), so a 40MB message with a 35MB attachment (over the 25MB legacy cap, extract/streaming.py:24 -> PermanentError, mime.py:249) writes a ~53MB sqlite row (known as A2 in docs/qa-findings.md, deferred).
  - Impact: Scenario 3: oversized messages cost a full download plus a DLQ write larger than the message itself; a burst of large messages inflates the state DB and memory instead of being rejected from metadata (Gmail exposes sizeEstimate via messages.get format=minimal, so a cheap pre-check is possible).
- **[medium] (consumer-value)** "Provider-agnostic" is one provider in practice: Graph is not exposed via connect() and never validated live
  - Evidence: connect() raises ValueError for anything but memory/gmail (src/mailflow/facade.py:303) — "graph is wired but not exposed here yet" (:236); status pages admit Graph is "code-complete; needs a live Exchange mailbox to validate" (docs/mailflow-showcase.md:60, :398) and the spec lists "Microsoft (parked)" (docs/mailflow-spec.md:302). Using Graph means the low-level run_service with 8 hand-wired stores/emitters (README.md:207-215) — none of the connect() ergonomics (filters specs, fields, stages, state=).
  - Impact: The unified Gmail+Outlook contract is the differentiator vs writing directly to one vendor SDK. A buyer with Microsoft 365 mailboxes — the majority of enterprises — gets an unvalidated adapter behind an expert-only API, so the pitch "write your app once" is not deliverable today.
- **[medium] (consumer-value)** No multi-account story: one refresh token per connect(), no end-user OAuth onboarding, no historical backfill
  - Evidence: GmailConfig binds a single oauth_refresh_token_ref to the whole config (src/mailflow/adapters/gmail/config.py:27-29) and connect() builds one token provider from one credentials dict (src/mailflow/facade.py:372-378); the only consent helper is a developer CLI script (scripts/get_gmail_refresh_token.py). The cursor is seeded at watch time (bootstrap_watches, live.py:243-248) — there is no API to import existing/older mail.
  - Impact: CRM sync, recruiting, or any SaaS ingesting N users' mailboxes must build per-user OAuth consent, token storage, rotation persistence, and one process/handle per account themselves — the exact undifferentiated plumbing Nylas/EmailEngine sell. And on day one the library sees only mail arriving after connect, so "process our invoice inbox" starts from an empty history.
- **[low] (consumer-value)** Docs contradict the code and each other — trust-eroding drift for evaluators
  - Evidence: README.md:171 claims SCHEMA_VERSION "1.1" while code ships "1.3" (src/mailflow/core/events.py:14, echoed correctly in docs/mailflow-usage-guide.md:385); README's scope table (README.md:163-169) still lists the Gmail adapter as future "Plan 3" while the same file documents live Gmail below (:225+); docs/mailflow-usage-guide.md:31 instructs `pip install mailflow` though the package is unpublished (docs/mailflow-showcase.md:399 "Publish / SaaS deferred", INSTALL.md wheel handoff).
  - Impact: An evaluating engineer following the usage guide's first command hits a nonexistent (or squatted) PyPI name, then finds version claims disagreeing across three docs — cheap credibility losses during exactly the first 10 minutes of evaluation.

## Deployment fitness matrix

| Infrastructure | Status | Why |
|---|---|---|
| **AWS Lambda / Cloud Functions** | ❌ Blocked | `run_service` is a blocking pull loop with daemon-thread schedulers (watch renew, sweep); no per-event entrypoint exists. A serverless mode needs an invoke-per-notification `fetch_new()`-style entrypoint plus a shared (non-sqlite) cursor/dedupe store — the ports allow it, no adapter exists. |
| **Cloud Run / long-running container** | ⚠️ Works with caveats | Natural fit, but adopters must hand-write: process wrapper, `/healthz`/`/readyz`, SIGTERM graceful shutdown, metrics. Nothing ships. Single replica only. |
| **EC2 / VM + systemd** | ⚠️ Works with caveats | Same hand-rolled harness; no CLI entrypoint (`mailflow run --config …` does not exist), no structured logging/metrics export. |
| **Kubernetes (multi-replica)** | ❌ Unsafe | No shared state store, no leader election; two replicas on one mailbox double-process and corrupt cursor semantics. Constraint is undocumented. |

## Prioritized roadmap

**P0 — make the core promise true (silent-loss fixes; blocks all production adoption)**
1. Pipeline: stop the stream on the first non-terminal disposition (or commit only the lowest contiguous terminal cursor) — `core/pipeline.py:143-150`. (C1)
2. Gmail: stamp each `RawMessage` with its *own* history-record id, not the batch-final `historyId` — `adapters/gmail/provider.py:69,85`. (C11)
3. Gmail: seed the bootstrap cursor only when the store is empty — `adapters/gmail/bootstrap.py:24-27`. (C12)
4. Dedupe stores: attempts must survive `release()`; implement lease expiry (`claimed_at` + `lease_seconds`) in `SqliteDedupeStore`. (C2, C3)
5. Graph: wire `SubscriptionReconciler` + renewal scheduler into `run_service`; make Event Hub checkpointing outcome-aware; per-page deltaLink stamping in sweep. (C16-C18)
6. MIME: inline-disposition text parts are bodies, not attachments; catch charset `LookupError` → `errors="replace"`; handle `message/rfc822` containers. (C8-C10)
7. Facade: propagate live-thread failures into `stream()` (error sentinel through the queue) + add `stop()/close()`. (C7)

**P1 — trust & first-contact DX (what evaluators hit in hour one)**
8. Fix `state="sqlite:///mf.db"` path resolution (SQLAlchemy convention) — `config/state.py:30-37`. (C4)
9. Sweep all docs + feature explorer for the `on_filtered="tag"` default; fix the inverted “only invoices” recipes. (C5, C6)
10. LICENSE + PyPI metadata + `py.typed` + CHANGELOG; publish the package.
11. Eager validation of `connect()` inputs (credentials dict, filter specs, unknown params fail loudly).

**P2 — production operability**
12. `mailflow run --config …` console script: SIGTERM handling, `/healthz`+`/readyz`, structured logs.
13. Wire durable DLQ through `connect()` (sqlite state ⇒ `SqliteDeadLetterStore`); expose `mf.dead_letters()` / `mf.redrive()`; stop defaulting `dlq_emitter` to a discarded `MemoryEmitter`.
14. Observability: `on_report` callback / counters, minimal Prometheus/OTLP export.
15. sqlite hardening: WAL + busy_timeout, atomic `commit_if_ahead` (single UPDATE…WHERE), 0600 file perms, done-row TTL sweep; atomic `LocalBlobStore` writes (temp + rename); atomic `FileTokenRotationSink` + load-back at startup.
16. DLQ PII: cap/externalize `raw_b64`, retention TTL, fix the docstring claiming no content is persisted. Guard filter regexes (validate patterns, cap header length).

**P3 — growth: what makes people *choose* it**
17. Polling-only Gmail mode (no Pub/Sub) as the quickstart — collapses time-to-first-email from days of GCP provisioning to minutes.
18. Public attachment-bytes API (`mf.open_attachment(...)`) — unblocks invoice/AP, document-pipeline, recruiting use cases.
19. Expose `provider="graph"` through `connect()` and validate live — make “provider-agnostic” true; or add a stdlib-`imaplib` IMAP provider for everything non-Google/MS.
20. Per-mailbox parallelism (serialize within, parallel across) as the V1.5 scaling unit; then a shared-store (Redis/Postgres/Firestore) adapter for horizontal scale.
21. Multi-account story: end-user OAuth onboarding helpers, N-mailbox management, historical backfill.

## Consumer-value summary (who benefits, honestly)

- **Realistic persona:** a Python backend/AI-automation team that wants “mailbox → one clean object
  in *my* pipeline, self-hosted, mail never touching a third party.” Against Nylas/Unipile pricing
  and data-custody concerns, and against DIY `google-api-python-client` code (which invariably
  botches dedupe/cursor/watch-renewal), this is a genuinely compelling wedge.
- **Use-case coverage today:** invoice/AP and recruiting-inbox flows work end-to-end *except*
  there is no public way to read attachment bytes; support-ticket and CRM sync need
  reply/labels/threading/multi-user OAuth (absent); phishing triage lacks raw-message and
  auth-results access.
- **The “you store the email, we don't” stance** is a strength (data custody, GDPR posture) —
  but it obligates the library to be flawless about *delivery*, which is exactly where the
  confirmed defects are, and it is quietly contradicted by the DLQ persisting full raw messages.
- **Table stakes still missing** vs alternatives: IMAP (non-Google/MS mail), sending/replying,
  threading model, search, OAuth consent-flow helpers, multi-account, outbound webhooks.
