V1 Technical Overview

How each core feature of the shipped Gmail library actually works — the mechanics behind the compose-your-pipeline surface and the always-on reliability guarantees. Written to answer the questions a reviewing engineer will raise, not to restate the API.

Overview

The two ideas that explain everything else

mailflow is a library other programs embed. It watches a Gmail inbox and turns each raw message into a clean, structured CleanEmail event. Everything below is a variation on two ideas:

Idea 1 — a pipeline you compose. Every email flows through the same seven stages. You add optional behaviour at the stages you care about (which mail, which fields, how to transform); the rest is defaulted.

Idea 2 — reliability you don't wire. A band of guarantees runs underneath every message, whether or not you opt into anything. This is the actual product: you don't assemble correctness, the pipeline enforces it.

always on dedupe monotonic cursor size guard (fail-closed) retry → DLQ at-least-once storm containment 401 → refresh-once durable DLQ + redrive attachment cap blob dedupe scope check metrics + health
The one rule to remember

Notifications are wake-signals only. A Gmail push never carries an email and is never trusted to name "the message to fetch." It carries a historyId watermark that only means "go check your inbox from your saved bookmark." The durable cursor — not the push — is the source of truth. Pushes can be forged, replayed, duplicated, or lost; none of that can corrupt or skip the stream, because the cursor is what decides what to fetch.

Part 1 · The pipeline

One email, end to end

Follow a single message from "you have mail" to a delivered event. Each numbered step names the stage and the guarantee that fires there. Green rings are terminal — the cursor advances.

A push arrives — and is treated as a nudge
Gmail Pub/Sub delivers (emailAddress, historyId). The runtime parses it and submit()s the watermark; it fetches nothing yet. If the push is lost, a periodic sweep triggers the same check anyway.
Fetch the delta from the saved cursor
The provider loads the stored historyId and asks Gmail "what changed since here?" — history.list → new message IDs. The push's own number is only ever an upper bound to sync toward.
Claim the message (dedupe)
try_claim(idempotency_key) takes an exclusive lease. Key = (tenant, mailbox, provider_message_id). Already claimed/done → this is a duplicate, short-circuit to terminal.
Size guard — before any download
The provider reports the message size. > 50 MB, or unknown/zero, → dead-letter now (fail-closed: if we can't vouch it fits, we never pull it).
Parse the cheap envelope, then filter
Sender/recipients/subject are parsed before the body. Filters run on this cheap Envelope, so a dropped email costs no body download or extraction.
Extract → CleanEmail
Fetch the full RFC822 (format=raw), MIME-parse it, pull fields, stream attachments to the blob store, derive identity + thread key + bounce/auto flags.
Clean, then run your stages
The default cleaner backfills body_text from HTML if empty. Your clean_fn runs first, then stages transform or drop the email.
Emit & mark done — cursor advances
An EmailEvent (schema 1.3, stamped with the idempotency_key) reaches your consumer. mark_done() closes the claim and the cursor commits forward. Every terminal outcome — emitted, dropped, duplicate, dead-lettered — advances the cursor; only a transient retry does not.
Why this order matters

Claim → size-guard → filter all happen before the expensive fetch/extract. A duplicate, an oversized message, or a filtered sender is disposed of cheaply, and each still moves the bookmark forward so the stream never re-examines it.

Part 2 · Deep dives

01Ingestion & the cursor

How it works

Gmail push (Pub/Sub) is a wake-trigger, not a delivery channel. The runtime decodes the notification to (emailAddress, historyId) and buffers the watermark. Fetching is a separate delta poll: from the durable cursor, Gmail's history.list returns the IDs that changed since. Poll — not push — is authoritative, so lost or forged pushes cannot corrupt the stream. A background sweep runs the same delta on a timer as a safety net.

The cursor is Gmail's historyId, stored per (tenant, stream) with a monotonic order. It advances through commit_if_ahead() — a compare-and-set that rejects any value ≤ the stored one. It can never slide backward, and it advances on every terminal disposition, not just successful emits.

If a push is forged or replayed, can an attacker inject or skip mail?

No. The push only supplies a watermark to sync toward; the actual message list comes from Gmail via the trusted delta. A forged historyId can at worst ask us to re-check the inbox — the monotonic cursor and dedupe make redundant checks harmless.

What happens on crash / restart mid-stream?

On boot the pipeline reloads the stored cursor and resumes the delta from exactly there. Nothing is missed (the cursor only advanced on terminal outcomes) and nothing is re-delivered (dedupe claims persist in SQLite state).

First run, with no cursor yet?

Bootstrap arms the Gmail watch() and seeds the cursor with the historyId that watch returns — so the first delta starts from "now" rather than replaying history.

The historyId aged out of Gmail's ~7-day window?

Gmail raises a stale-history error; the provider re-seeds the cursor to the current historyId from the profile and continues. Mail inside the lost window is skipped rather than the stream jamming — a deliberate availability-first choice. (Honest note: that skip isn't logged or metered today, so add a gap counter before you depend on it in production.)

How is the "watch" kept alive?

Gmail watches expire in ~7 days. A daemon IntervalScheduler re-calls watch() daily (Gmail has no renew endpoint — renewal is re-watching). Scheduler failures are swallowed so the loop never dies.

Which folders does it watch — everything, or just the inbox?

INBOX only by default (label_ids=["INBOX"]), and both the watch and the delta filter on it. Mail that a Gmail rule files straight into another label won't trigger a notification or the sweep unless you configure the labels you care about.

What if pushes arrive out of order, or the same one twice?

Harmless. A push only carries a watermark to sync toward; the real work is the delta poll from the durable cursor. Order and duplicates wash out — the monotonic cursor and dedupe make redundant or reordered nudges a no-op.

A push and the timed sweep firing at the same moment — double work?

They can overlap, but they run the same delta and every message is claimed once via try_claim, so the second one just loses the race and exits. Worst case is a little wasted API quota, never a double-emit.

02Fetch & extract → CleanEmail

How it works

The pipeline fetches the message as format=raw — the complete RFC822 bytes, base64url-encoded — and decodes them. That single blob is parsed with Python's standard email library into a MIME tree, and the extractor reads structured fields off it: sender/recipients, subject, dates, body_text / body_html, thread key, attachments, and the classification flags. There is no reliance on Gmail's parsed-JSON view — the raw bytes are the single source, which also lets us hash exact content.

Identity. Two keys are derived. The idempotency_key is (tenant, mailbox, provider_message_id) — the dedupe/wire fingerprint. The canonical_id is the RFC Message-ID when it's trustworthy (well-formed <local@domain>), otherwise a stable sha256(provider, provider_message_id, mailbox).

Why format=raw instead of Gmail's parsed full view?

One fetch yields the exact on-the-wire bytes, so MIME parsing, body extraction, and attachment hashing all operate on identical content — no divergence between "what Gmail parsed" and "what we stored," and no second round-trip.

How is the conversation thread carried?

Gmail's threadId rides onto CleanEmail.thread_key. If a provider ever supplies none, we fall back to a normalized subject (strip Re:/Fwd:, lowercase, collapse whitespace) so a reply still groups with its root.

What if the Message-ID is missing or malformed?

It's treated as untrusted and canonical_id falls back to the stable hash. Dedupe never depends on canonical_id anyway — it uses the provider-scoped idempotency_key.

Plain text or HTML — which body wins?

The real text/plain part wins when present; HTML→text is only synthesized to fill a blank body_text. So a proper multipart email delivers the sender's actual plain text, not a re-derived approximation.

Malformed or pathological MIME — does extraction crash?

No. Python's email parser is lenient: missing headers, odd charsets, or broken parts degrade to empty fields rather than throwing. A genuinely unusable payload (e.g. invalid base64) is classified permanent and dead-lettered, not retried forever.

Is the From address trusted for identity?

It drives direction and canonical identity; Return-Path and Sender are captured but not used as a trust signal, and V1 does no DKIM/SPF. So a spoofed From isn't detected here — treat sender authenticity as the consumer's concern.

03Attachment handling

The mechanism, precisely

In the ingest pipeline there is no marker-then-fetch dance. The whole message already arrived as format=raw base64url bytes; attachment parts are just nodes in the locally-parsed MIME tree. Each part is streamed out of those bytes in ~64 KB chunks, decoded, SHA-256'd, and written to a content-addressed blob store. A separate Gmail messages.attachments.get endpoint (the classic attachmentId → base64 → decode flow) does exist, but it is wired only to the optional on-demand get_attachments(id) API — not to ingestion.

How it works

MIME part→ classify real / inline→ allowlist check→ stream + SHA-256 (cap)→ scanner→ blob store (dedupe)
on violation, no policy → dead-letter whole message (fail-closed)
on violation, with policy → strip part + record on stripped_attachments + deliver

The per-attachment cap is 25 MB, enforced mid-stream: the streamer raises the instant the running byte-count crosses the cap, so an over-cap file is never fully buffered. Storage is content-addressed — the blob key is the SHA-256 of the bytes — so the same attachment across two messages is written once (dedupe is a file-exists check).

Do we get a marker per attachment and then call an API to fetch it?

Not in ingestion. The bytes come inline inside the raw message; we stream them out of the MIME tree locally. The marker+attachments.get+base64 path is only used by the opt-in on-demand retrieval API.

Is the whole file loaded into memory to check its size?

No. It's streamed in chunks while hashing; the size check trips mid-stream and aborts. That's how "fail-closed on oversize" is physically guaranteed rather than checked after the fact.

How does the message-level 50 MB guard relate to the 25 MB per-attachment cap?

They're orthogonal. The 50 MB guard rejects the whole message before download (and fails closed on unknown size). The 25 MB cap applies to each individual part during the MIME walk.

What happens to an over-cap or blocked attachment?

Default (no policy): fail-closed — the entire message is dead-lettered (quarantined, not silently dropped). With an attachments= policy: strip-and-deliver — the offending part is removed, its metadata appended to email.stripped_attachments with a reason (oversize / not_allowlisted / unreadable / scanner), and the message is delivered.

"Real" vs "inline" — what's the distinction?

Real = Content-Disposition: attachment (or a filename with no inline disposition). Inline = Content-Disposition: inline or a Content-ID (embedded logos, tracking pixels). A policy can apply different size/type rules to each class.

Is there virus scanning?

There's a seam: a swappable AttachmentScanner.scan() port. V1 ships a no-op allow-all default and an empty allowlist (allow-all); a real AV/CDR scanner is the designed-for extension point, deferred to a later plan.

Is the content-type trusted, or sniffed from the bytes?

Trusted from the MIME header — there's no magic-byte sniffing, so a .exe mislabeled text/plain would pass a type allowlist. Real content inspection is exactly what the scanner seam is for.

If an inline image is stripped, does body_html get fixed?

No — a stripped inline part leaves its cid: reference in the HTML for the consumer to handle; rewriting inline-image references is a later plan (the seam is there).

How durable is the blob write itself?

The reference local store writes content-addressed straight to its final path; a crash mid-write can leave a truncated blob that the exists-check won't heal. It's a dev-grade store — the intended production swap is an S3/GCS adapter with temp-then-rename, behind the same BlobStore port.

Eager now vs on-demand later — do we even need blob storage?

This is a real design axis, not a fixed answer. mailflow already ships both paths: the ingest pipeline is eager (streams every attachment to a content-addressed blob store), while get_email/get_body/get_attachments(message_id) are lazy — they re-fetch the whole message live via messages.get(format=raw) and parse the bytes back out. Ingest keeps the durable provider_message_id, so on-demand re-fetch needs nothing but that ID.

"After how many days can we still fetch on-demand?"

There is no fixed API TTL. A message and its attachments stay retrievable for as long as the message lives in the mailbox — effectively indefinite for normal inbox mail. The hard floors are: ~30 days after it's moved to Trash or Spam (auto-purge), immediately on a permanent delete or account deletion, and whenever a retention / Vault policy expires it. Do not confuse this with the ~7-day history window — that only limits delta detection (which new IDs we can discover), never whether a known message can be fetched. On-demand reads also require the OAuth token to still be valid at read time.

Why the design re-fetches the whole message rather than caching Gmail's per-part attachmentId: a Gmail attachmentId is not stable — it's scoped to one message fetch and can change, so you'd have to re-list the message to get a current one anyway. The messageId is the only durable handle, which is exactly what ingest persists. (The attachments.get endpoint is wired in the client but currently unused.)

Always ingest metadata + the durable re-fetch key (provider_message_id, filename, type, size, and the cheap SHA-256) and fetch bytes on demand — except for a selectively eager-stored subset (small parts, allowlisted types, anything that must be AV-scanned or audited). Pick eager as the default when you need durability past mailbox retention, compliance/audit, at-ingest scanning, or low-latency frequent reads; pick lazy when attachments are rarely opened, storage/PII-minimization matters, and messages are long-lived.

Two honest caveats about today's code before you rely on "lazy = no storage": the on-demand path currently still writes blobs (it passes the blob store into extraction), and there is no metadata-only ingest mode yet — so true lazy is a small code change, not a config flag.

04HTML → text cleaning

How it works

Cleaning is a swappable ContentCleaner port. The default is deliberately gentle and idempotent: if body_text is empty but body_html exists, it backfills the text (drop <script>/<style> blocks and tags, unescape entities, collapse whitespace). The same fallback also runs inside extraction, so an HTML-only email never delivers a blank body. Aggressive stripping (quoted-reply / signature removal) is a deliberately-out-of-scope opt-in for a later plan — the port exists so it slots in without a breaking change.

Is my HTML ever mangled or aggressively rewritten?

No. The default only backfills missing plaintext; it never touches existing body_text and never mutates body_html. Because V1 delivers plain text only (no HTML rendering), there is intentionally no HTML sanitizer.

Any risk on a huge or malformed HTML body?

The backfill is regex-based tag stripping with no hard timeout, so a pathological or very large HTML body carries some worst-case CPU cost on the single worker. Fine for ordinary mail; a proper parser/sanitizer is the later-plan path if you ever render HTML.

05Filtering

How it works

Filters evaluate against the cheap Envelope before the body is parsed — so dropping mail is nearly free. A filter chain returns the first decisive KEEP/DROP; anything else is UNCERTAIN and falls through to the next filter. Empty configs are safe no-ops. Eleven built-in kinds ship, plus your own lambda env: … predicate.

Difference between whitelist and only_domain?

whitelist keeps a match and stops the chain but lets non-matches continue to other filters. only_domain is a strict allow-list — it actively drops anything not in the set.

Are user-supplied regexes safe to run?

They run via re.search with no timeout, so a catastrophic (ReDoS) pattern could stall the single worker. Keep subject/to/cc patterns simple and anchored — this is trusted-input territory, not a place for arbitrary attacker-controlled regex.

What if a custom predicate throws?

It's treated like any processing error — retried, then dead-lettered — not silently swallowed. Write predicates to be total (guard against missing fields) so a bug doesn't quietly quarantine mail.

How are addresses matched — case, sub-addressing, IDN?

Exact-address matches are lowercased; regexes are case-sensitive unless you add (?i). Sub-addressing (+tags) and internationalized (punycode/IDN) domains are not normalized — match on the exact form you expect to see.

06Classification seam

How it works

Every CleanEmail carries two booleans derived at extract time and shipped on the event (schema 1.3). is_auto_submitted is true when an Auto-Submitted header is present and isn't literally no (RFC 3834 — vacation/auto-replies). is_bounce is a thin heuristic: a daemon sender (mailer-daemon/postmaster), a null Return-Path (<>), or a multipart/report; delivery-status body (RFC 3464 DSN).

Is this full bounce/DSN parsing?

No — it's a seam exposing simple yes/no flags so consumers can route NDRs and auto-replies today. Full RFC 3464 classification is deliberately a later plan.

How reliable are the flags — false positives?

They're heuristics: a real person at postmaster@, or a manually forwarded delivery report, can trip is_bounce. Treat the flags as routing hints, not ground truth — don't hard-auto-delete solely on them.

Can a sender spoof these flags?

Yes — Auto-Submitted and Return-Path are sender-set and unauthenticated, and V1 does no DKIM/SPF. So don't use the flags as a security control, only as a convenience for routing well-behaved mail.

07Dedupe & at-least-once

How it works

Delivery is honestly at-least-once: on failure and replay the same email can reach you twice, so every event is stamped with the idempotency_key for you to dedupe on. Internally, a dedupe store guards work with a four-call lifecycle:

  • try_claim(key, lease) — take an exclusive lease before any work; a lost claim means "duplicate", short-circuit.
  • record_attempt(key) — bump the retry counter.
  • mark_done(key, ttl) — terminal; the claim sticks for a 60-day TTL so replays are recognised.
  • release(key) — transient failure; hand the claim back so a later run retries.
Why not exactly-once?

Exactly-once across a network + crashes is impractical; the honest, documented contract is at-least-once + a stable idempotency_key. The same shape backs both the in-memory store and the SQLite one, so a future Redis/Firestore adapter with lease-expiry drops in without changing callers.

What if processing outlives the claim's lease?

In V1 it can't cause a double-process: the shipped stores don't actually expire leases, and there's a single worker, so no one steals the claim. Lease-expiry is intentionally left for a real distributed store — the port shape already anticipates it.

What should the consumer actually do with the idempotency_key?

Treat it as the natural key and upsert/dedupe on it. Because transport delivery is at-least-once, the same event can legitimately arrive twice; keying on the idempotency_key collapses those to one.

08Reliability & the DLQ

How it works — one taxonomy, three reactions

Every failure is sorted into one of three types, and each reacts differently:

Auth · 401

Force one token refresh, retry the message once. A second failure → DLQ. Bounded by straight-line control flow, not a counter — no refresh loop.

Permanent · 403 / 404 / 410 / bad-base64

Will never succeed. Dead-letter immediately — no retry. This is what stops "poison loops" on deleted or garbled mail.

Transient · 429 / 5xx / network

Backoff and retry up to 3 attempts: exponential 2^n + jitter, honoring Retry-After. Then dead-letter.

Storm containment. Concurrency is capped by a bounded semaphore (default 8 in-flight); when saturated the client sheds load — raises a transient error immediately rather than queueing — so a flood of "slow down" responses can't pile up and crash the run.

Durable DLQ + redrive. A dead-letter persists a full record (including the base64 RFC822 bytes) to a DeadLetterStore. redrive() rebuilds each message and runs it through a fresh pipeline with a throwaway dedupe store, so a previously-quarantined message gets a clean second chance once the root cause is fixed; the original idempotency_key rides along so downstream still dedupes. Poison isolation is per-message — one bad email is quarantined, never crashing the batch. (Counting contract: only add_dead_letter() increments the DLQ counter, so one poison message is counted exactly once.)

Why does an unknown-size message get dead-lettered instead of downloaded?

Fail-closed: if we can't confirm it's under budget, we refuse to pull it. Better to quarantine and inspect than to blow past the size limit on a message that lied about its size.

Can one broken email stall the whole inbox?

No. It's isolated to the DLQ, the cursor advances past it (dead-lettered is terminal), and processing continues. You replay it later via redrive().

What if the DLQ store itself fails to persist a record?

The message is not marked done, so it stays reclaimable and re-dead-letters on a later run — no silent loss. Durability is ordered so the quarantine write happens before the claim is closed.

A dropped-by-filter email isn't in the DLQ — recoverable if I fix the filter later?

No. A filter drop is terminal and the cursor has moved past it, so correcting a filter afterwards needs a bounded re-scan/backfill, not a DLQ redrive. Tune filters conservatively.

Could a giant Retry-After freeze everything?

Backoff sleeps on the single worker thread, so a very large server-supplied Retry-After would stall the run. Worth a hard cap on the honored value in production.

09State & persistence

How it works

One knob — state= — selects durability. "memory" is stateless (cursor, dedupe, and blobs live in RAM; you dedupe on canonical_id yourself), good for demos and tests. "sqlite:///mailflow.db" persists the cursor, the dedupe claims, and the DLQ to one pure-stdlib SQLite file, with attachments written to a sibling blob directory. Restart the process and it resumes from the stored cursor, skips already-done messages, and honours stored attempt counts — no external database required.

Can two processes run against the same SQLite file?

Not a supported configuration. V1 is single-worker — one connection guarded by a lock. The monotonic cursor + dedupe keep it correct if you tried it, but you'd hit lock contention and wasted double-fetches. Run one instance; restarts of that one instance are safe.

How durable is it on a hard crash or power loss?

Commits survive an ordinary process restart (that's the point of SQLite state). Hardening for power-cut durability (WAL/synchronous) and strict blob↔DB atomicity is a production-adapter concern, not something the reference SQLite store promises.

Can we swap SQLite for Postgres / Redis / S3 later?

Yes — cursor, dedupe, DLQ, and blob are all ports. A real backend drops in via overrides= (or a new state scheme) without touching pipeline code. That swappability is the whole reason the seams exist.

10Secrets & token rotation

How it works

Credentials come through a SecretProvider (V1 keeps it simple — one delegated OAuth refresh token per mailbox, resolved from an env:// ref). When Google rotates the refresh token, the client compares before/after and, if a rotation_sink is wired, hands the new token to it to persist (the file sink writes 0600). Scope is verified at startup by default — a missing gmail.readonly fails fast rather than mid-run.

Known gap — worth stating up front

Rotation persistence is only half-wired. The sink is called on rotation and writes the new token, but nothing reads it back at startup — the library re-initializes from the original configured token. So a rotated token is effectively lost on restart unless the consuming app loads the persisted value itself (or you back the secret with a rotating store). Close this loop before relying on long-lived unattended runs.

Concurrent 401s — is there a refresh storm?

Each in-flight request can trigger its own single refresh (there's no shared refresh lock), so a burst of simultaneous 401s could hit the token endpoint a few times. Harmless at single-worker scale; a coalescing lock would be the fix if you parallelize.

Does the startup scope check ever pass without really checking?

On older google-auth that doesn't report granted scopes it fails open — it trusts the requested scopes rather than the actual grant. A documented caveat; on current libraries it verifies the real grant and fails fast on a missing gmail.readonly.

11Consumption API

How it works

One front door: connect(provider, …) returns a Mailflow handle. You pick how to consume and layer optional knobs — filters (which mail), fields (project to a trimmed dict), clean_fn + stages (transform/drop), attachments (policy), state, overrides.

Order is enforced: filters see the cheap envelope pre-body; clean_fn runs first among processors; stages see the full CleanEmail and drop it by returning None/False. fields=[…] projects the delivered object to a trimmed dict (accepting "from" as an alias for from_).

Slow consumer on a live stream() — backpressure?

The live path buffers into an effectively unbounded queue, so a consumer that drains slower than mail arrives grows memory. Keep the consumer fast, or batch/offload — there's no built-in backpressure yet.

What if my stage or on_email callback throws?

It's caught and treated as a processing failure (retried, then dead-lettered), so it won't crash the loop — but it also won't surface as an exception to your caller. Watch the DLQ, and keep callbacks defensive.

Lifecycle — clean shutdown, or calling stream() twice?

The live loop runs on a daemon thread with no graceful-stop or reentrancy guard today, so run one stream per handle and rely on process exit to stop it. A close()/context-manager seam is a reasonable near-term addition.

12Observability

How it works

Every message produces a DecisionTrace — including drops — logged through the stdlib logger (mailflow.pipeline) with its disposition, stage, and reason, so "why was my email dropped?" is always answerable. A RunReport.counters() returns a plain dict (fetched / emitted / dropped / duplicate / dead_lettered / attachments_stripped) — a dependency-free metrics seam, no Prometheus/OTel required. health() probes the cursor, dedupe, and blob stores (the dedupe probe does an atomic claim+release on a reserved key so it never corrupts real state).

Are the counters and run reports persisted?

No — RunReport is per-run and in-memory; the live runtime doesn't aggregate it across runs. counters() is a pull seam you scrape into your own metrics system; nothing survives a restart on its own.

Would I actually know if the watch silently died?

Not easily today — the renewal scheduler swallows errors and health() doesn't probe the subscription, so an expired watch still reports "healthy" while the timed sweep is the only backstop. Add renewal logging + a watch-liveness (and cursor-momentum) check before production alerting.

Log volume at scale?

One INFO line per message (with the drop reason). At high throughput you'll want level control / sampling and a JSON formatter to feed a log pipeline — the trace content is there, the shipping policy is yours.
